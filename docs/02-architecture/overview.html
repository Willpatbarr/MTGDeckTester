Architecture Overview

What this is: the component layering, the three internal diagrams, and the six non-negotiable architectural principles the app is built on.  What to do with it: read this before touching any engine, view, or model code.

One-sentence version

Views talk to ViewModels, ViewModels only ever send human actions into GameEngine, GameEngine is the sole authority on game state and asks AIEngine for decisions the same way it would ask a human, and six principles keep that arrangement from eroding.

Architectural principles

These six principles govern every future decision in this codebase. When a future change seems to conflict with one of these, the principle wins by default — reopen it explicitly, don't drift past it silently.

Do not fix this by mistake

Principle 1 — Strict engine, permissive UI. The engine is rules-accurate. The UI is a testing tool: it shows all hands and libraries, offers every zone destination, and never blocks an action. A future contributor who notices "the UI lets you do illegal things" and tightens it has broken the product on purpose disguised as a bug fix. See contradiction C10.

Principle 2 — The UI never infers rules state

Attackers, blockers, attachments, layers, and legality are explicit GameEngine state, read by the UI, never derived in it. If a view has to compute a rules answer itself, that logic belongs in the engine instead.

Principle 3 — One decision pipeline

Humans and AI answer the same DecisionRequest. The AI never mutates state directly — it only ever produces a DecisionResponse, exactly like a human would.

Principle 4 — Determinism is load-bearing

Every random choice goes through the game's seeded generator. Replay is exact, which is what makes undo, redo, save, load, and step-through replay all possible on top of the same action history.

Principle 5 — Layout is not game state

Moving a card within a zone is a layout operation. It produces no GameAction, is not undoable, and is excluded from replay.

Do not fix this by mistake

Principle 6 — Rules knowledge is a subsystem, not a service. No RulesEngine type exists. Rules knowledge lives in the Rules System subsystem inside GameEngine, queried synchronously by the Action Processor. A future contributor who "notices" GameEngine and AIEngine both exist as peer engines and adds a peer RulesEngine to match is undoing a deliberate decision, not correcting an oversight. See contradiction C5.

Principles 1 and 6 both came out of resolved conflicts between sources, not from a clean original design. See ../00-source/contradictions.html for the full reasoning behind C5 (where the rules live) and C6 (application layering).

What to do next

  1. Read data-model.html for the field-level shape of every model named in the layering diagram.
  2. Read conventions.html before writing any engine code — it enforces principles 3, 4, and 6 as concrete rules.
  3. If a change seems to require breaking one of the six principles, treat that as a decision worth writing down, not a silent edit.
