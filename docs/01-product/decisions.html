Decision Log

Product and architecture decisions, including the seven proposed defaults that need review.

One-sentence version

Most of the plan is already decided or locked from source material; seven genuine coin-flips remain open in the Proposed section below, and the biggest one — building a full rules engine — is the single call that reshapes the whole project.

Proposed — read these first [PROPOSED]

Seven genuine coin-flips. Each has a default already chosen so the plan can move forward, but every one of these is worth a deliberate yes.

P1 · Proposed · the biggest call in the whole plan

Full rules engine (resolves conflict C1)

Default chosen: build it — the newer, more detailed spec (S2) wins over the older, simpler one (S1).

You get a real MTG sandbox that can eventually test anything a card does, at roughly 10× the MVP size that the older spec described. The alternative is S1's Simple Bot Mode: playable in about a month, but creatures are vanilla and it can never test what a card actually does. This single decision reshapes the entire milestone tree — see milestones.html, where M2 is deliberately front-loaded so a usable manual sandbox exists before any of this rules work begins.

P2 · Proposed

Local persistence technology (resolves gap G1)

Default chosen: SwiftData for decks and the card cache; Codable JSON for game saves and replays.

SwiftData gives free querying and a path to iCloud sync later, but its migration story is still young. JSON keeps replay and save files portable and diffable, which fits — a game save is a document, not something you query.

P3 · Proposed

Priority auto-pass timer (resolves conflict C8)

Default chosen: off by default.

On by default matches S2's literal text, but it actively fights the manual-advancement default and can steal priority while you're still thinking about a line. Off means you never lose a beat; it's a setting you can flip on for fast goldfishing.

P4 · Proposed

Battlefield stays fixed and non-scrolling (resolves conflict C13)

Default chosen: ship as specified in MVP — no zoom, no pan, no scroll.

This is the simplest build and preserves the freeform drag model, but a real Commander board will outgrow an iPhone screen (roughly 12–15 cards before it's unusable). Trigger for pinch-zoom or an auto-organize "Clean Up Board" feature is the first game where you actually run out of room.

P5 · Proposed

AIEngine over BotEngine (resolves conflict C7)

Default chosen: AIEngine.

Pure taste — the diagrams say AIEngine, the prose says BotEngine. Picking one now means the codebase never has to carry both names for the same component.

P6 · Proposed

AI difficulty scaffold in M5

Default chosen: build the scaffold now, ship exactly one strategy.

Costs a little extra structure up front, but avoids a rewrite the moment a second difficulty level is wanted. If you're confident there will only ever be one bot strategy, this scaffold can be dropped.

P7 · Proposed

GitHub Actions deferred to T2

Default chosen: deferred, not set up now.

macOS runner minutes burn at 10× the private-repo rate, so the free 2,000-minute allowance is really only about 15–20 iOS builds a month. Trigger for revisiting is the second time a broken build gets pushed to main.

Conflicts [CONFLICT]

Full detail, both source positions, and reasoning live in contradictions.html — not duplicated here. One-line resolutions only:

  • C1 — depth of the rules engine: full engine wins (see P1 above).
  • C2 — Simple Bot Mode: dropped; kept on record as the fallback if the rules engine slips.
  • C3 — format & life total: Commander, 40 life, commander rules on.
  • C4 — card data source: Scryfall; free-form token creation dropped in favour of a deck-derived picker.
  • C5 — where the rules live: a Rules System subsystem inside GameEngine, not a peer RulesEngine.
  • C6 — application layering: MVVM with ViewModels, Database, and CardAPI as shown in the diagrams.
  • C8 — priority timeout vs. manual advancement: both real, timeout ships off by default (see P3 above).
  • C11 — mulligans: in, as a silent regression to fix, not a decision to cut them. London mulligan.
  • C13 — fixed battlefield vs. iPhone-first: ship fixed for MVP, mitigation deferred (see P4 above and the Deferred table).
  • C14 — deck/role model: no conflict, both sources agree; recorded [LOCKED] so it isn't reopened.

Locked [LOCKED]

Everything tagged [LOCKED] in features.html came directly from the source specs and diagrams, not from planning judgment. If a locked feature looks wrong, the fix is to go back to the source material — not to relitigate it here.
