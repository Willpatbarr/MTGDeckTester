Sentry

Crash reporting setup for M7 and outside TestFlight builds.

What & why

Sentry captures crashes and errors from installed builds and reports them with stack traces, so the developer learns about a tester's crash without having to ask them what happened. It's the difference between "a friend says the app crashed" and an actual symbolicated trace to debug from.

Alternatives considered: Firebase Crashlytics (free and unlimited, but drags in the entire Firebase SDK and Google's data terms for a single feature) and Xcode Organizer (free, built-in, but only surfaces crashes from users who explicitly opted into diagnostic sharing — most testers won't). Sentry won on being purpose-built, lightweight to integrate, and not requiring a tester to opt into anything extra.

Setup steps

  1. Create a Sentry account and a new organization.
  2. Create a project, platform: Apple → iOS (Swift).
  3. Copy the project's DSN from Settings → Client Keys (DSN).
  4. Add the Sentry Cocoa SDK (Swift Package Manager) to the Xcode project.
  5. Initialize the SDK at app launch with the DSN, configuring it to run only in Release builds (or a dedicated TestFlight configuration) so local debugging noise doesn't count against the quota.
  6. If uploading dSYMs for symbolicated stack traces, generate a Sentry auth token under Settings → Auth Tokens and wire it into the build's dSYM upload step — keep this token out of the committed project.
  7. Verification: trigger a deliberate test crash (Sentry's SDK includes a test-crash helper) in a TestFlight build, and confirm it appears in the Sentry dashboard with a readable, symbolicated stack trace within a few minutes.

The DSN is safe to embed client-side because it's write-only, but it still belongs in configuration rather than hardcoded inline so it can differ between environments. Real secrets — the auth token in particular — are never committed to the repository.

Escape hatch

Lock-in: Low. Crash events are ephemeral diagnostic data, not anything irreplaceable — losing history on migration costs nothing structurally important.

Migrating off Sentry means swapping the SDK initialization for another crash reporter (Crashlytics, or back to Xcode Organizer) and updating the DSN/config. No data migration is needed since nothing downstream depends on historical Sentry events.
