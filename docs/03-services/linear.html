Linear

Verification guide for the existing team, project, milestones, and backlog.

What & why

Linear tracks the seven milestones and roughly 72 planned issues for this project, organized under team MTGDeckTester and project MTG Deck Tester (key MDT). It's where "what am I building next" lives, separate from the docs site's "why did we decide this."

Alternatives considered: GitHub Issues (would keep everything in one tool, but its milestone/cycle model is weaker and there's no reason to duplicate a tool the user already has a Linear habit with) and a plain markdown task list (loses the structured labels, filtering, and dependency links this project's issue graph actually needs). Linear won on being the tool already in use with the right feature set for milestone + dependency tracking.

Setup steps

Team and project already exist. These steps are a verification checklist.

  1. Confirm team MTGDeckTester exists (id da95790b-599f-433b-84c8-8123ad0ec6a3 per the master brief).
  2. Confirm project MTG Deck Tester exists under that team with issue key MDT.
  3. Confirm the 7 milestones from the plan (M1–M7) exist as Linear milestones or cycles, matching ../04-plan/milestones.html.
  4. Confirm the label set exists: area/models, area/engine, area/rules, area/ai, area/ui, area/data, area/services, area/docs, T0, T1, T2, proposed.
  5. Spot-check a handful of the ~72 issues against the list in the master brief to confirm titles, milestones, and labels line up.
  6. Verification: open the project view, filter by milestone M1, and confirm the 11 M1 issues listed in the brief are all present with the right labels.

Secrets & config

No secrets are needed for normal use — Linear is accessed via its web app or native app with the user's own login. If a Linear API key or MCP integration token is ever used for automation, it is server-side/local-only, never client-side, and never committed.

Escape hatch

Lock-in: Low. Issue content, titles, and comments export via Linear's CSV/API export. Nothing in the app depends on Linear at runtime — it is purely a planning artifact.

Migrating off Linear would mean exporting issues to CSV or JSON and re-importing into whatever replaces it (GitHub Issues, a markdown file, another tracker). Given ~72 issues, this is an afternoon, not a project.
