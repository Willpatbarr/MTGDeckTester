GitHub Actions

Deferred CI setup for build and test checks.

What & why

GitHub Actions would run the Swift Testing engine suite (see conventions.html) automatically on push, catching a broken build or a failing test before it's discovered by hand. Right now, that check happens manually, by running the tests locally before pushing.

Alternatives considered: Xcode Cloud (Apple's own CI, tightly integrated, but a second billing relationship and quota to track for a solo project) and Buildkite/CircleCI (more capable, but built for teams and overkill here). GitHub Actions won because it's already colocated with the repo and free minutes are available if the threshold below is ever hit.

Setup steps

Not applicable yet — this service is intentionally not set up. When the T2 trigger fires, the outline is:

  1. Add a workflow file at .github/workflows/build-and-test.yml in the repo.
  2. Configure it to run on a macos-latest runner, triggered on push and pull request to main.
  3. Steps: checkout, select the correct Xcode version, xcodebuild build, then xcodebuild test against the Swift Testing engine suite.
  4. Given the 10× minute multiplier, scope the workflow tightly — run it only on pushes to main and PRs, not on every branch push, to conserve the ~200 effective minutes/month.
  5. Verification (when this is actually set up): push a commit with a deliberately failing test and confirm the workflow run fails and is visible on the commit/PR; then fix it and confirm a green run.

Escape hatch

Lock-in: Low. A GitHub Actions workflow file is a small, self-contained YAML file. The actual build/test commands it runs (xcodebuild) are standard and not GitHub-specific.

Migrating to another CI provider means rewriting the same handful of steps in that provider's YAML dialect — an hour of work, not a rearchitecture.
