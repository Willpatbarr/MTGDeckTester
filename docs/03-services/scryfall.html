Scryfall

What this is: the runbook for the app's only genuinely load-bearing external dependency.  What to do with it: follow the setup steps once, then treat the caching rules as permanent — Scryfall is volunteer-run and has no paid tier to fall back on.

What & why

Scryfall supplies the complete MTG card database — names, mana costs, type lines, images, and (critically) all_parts token relations, which are what let the manual token picker limit itself to tokens a given deck can actually create. No card data means no deck import, no rendering, no token picker: the entire app is downstream of this one API.

Alternatives considered: MTGJSON (excellent bulk data, no image hosting, a heavier schema to map) and the magicthegathering.io API (stale, effectively unmaintained). Scryfall won because it is the only source with images, freshness, and token relations in one place.

Caching is a courtesy, not just an optimization

Scryfall is run by volunteers on donated infrastructure with no paid tier behind it. Hitting the rate limit gets you throttled and eventually IP-blocked — never invoiced. Aggressive local caching (the bulk file, plus a persistent image cache) isn't a performance nicety here; it's the price of being allowed to keep using a free service other developers depend on too.

Setup steps

  1. No account or signup — there is nothing to create.
  2. Set User-Agent: MTGDeckTester/0.1 (contact) and a proper Accept header on every outgoing request.
  3. Fetch https://api.scryfall.com/bulk-data and read the default_cards entry's download_uri.
  4. Download and parse the bulk file on first launch; persist parsed cards to SwiftData.
  5. Refresh weekly by comparing the bulk entry's updated_at against the last local refresh.
  6. For any card the bulk file doesn't resolve (a cache miss during import), fall back to GET /cards/named?exact=, respecting the same rate limit.
  7. Store image URLs from the card object, then cache the actual image bytes to disk yourself. Never hotlink Scryfall's image URLs at render time.
  8. Verification: import a decklist containing a double-faced card and a card that creates a token. Confirm both faces render correctly and the token shows up as an option in the manual token picker.

Secrets & config

No secrets exist for this service. There is no API key to protect. The only configuration value is the User-Agent string, which is not sensitive and is safe to compile into the client.

Escape hatch

Lock-in: Low. No data lives only at Scryfall — the downloaded bulk file and the image cache both live on the device's own disk once fetched.

Migrating to MTGJSON (the documented fallback) would mean rewriting the ingest parser and re-deriving the token-relation logic from a different schema — a parser rewrite measured in days, not weeks, with no data loss since nothing is stored server-side.

Cost & scale checkpoints

ScaleWhat breaks
~10 usersNothing. Each device downloads and caches its own bulk file independently.
~100 usersStill nothing. There is no shared quota — every user's traffic is their own device against Scryfall's public API, same as one user.
~1,000 usersStill nothing changes on the cost side. The only risk at any scale is a client bug that ignores the rate limit and throttles or blocks a user's own IP — worth a smoke test, not a budget line.

Teammate delta

None. There are no accounts, no seats, and nothing to share or provision. A second person building the app hits Scryfall exactly the same way the first person does.

What to do next

  1. Implement the bulk-data ingest and per-card fallback exactly as described above (Linear issues #4 and #5 under M1).
  2. Confirm the User-Agent header is actually being sent — some HTTP client defaults silently override it.
  3. Continue to the service map or on to milestones.
