GitHub

What this is: the canonical home for code, docs, and history — already set up.  What to do with it: use this runbook to verify the existing setup, not to create it from scratch.

What & why

GitHub hosts the private repository Willpatbarr/MTGDeckTester — the single source of truth for Swift code, the draw.io diagrams, and this docs site. It is also the trigger for the docs build: pushing to main is what Cloudflare Pages watches.

Alternatives considered: GitLab and Bitbucket both offer equivalent private-repo hosting, but GitHub was already the account in use before this project started, and switching would cost migration effort for zero functional gain on a solo project.

Setup steps

The repo already exists and is already in use. These steps are a verification checklist, not a from-scratch setup.

  1. Confirm the repo Willpatbarr/MTGDeckTester is set to Private under Settings → General.
  2. Confirm main is the default branch and that the working tree matches what's expected locally (git status clean, git log shows the expected commits).
  3. If GitHub Pages is ever wanted as a second docs host: Settings → Pages → Source → Deploy from branch → branch main, folder /docs. Note this will not activate on a private repo without a paid GitHub plan (Pro or higher). If it silently fails to activate, that is why — Cloudflare Pages is the documented fallback and is already the primary docs host, so this is optional, not blocking.
  4. Confirm branch protection (if any) matches intent — for a solo project, none is required; add it only once a teammate exists.
  5. Verification: push a trivial commit to main and confirm it appears on GitHub, and (once Cloudflare Pages is wired up per cloudflare-pages.html) that the docs site rebuilds within about a minute.
Painful to change later

Repository visibility and the org/username prefix (Willpatbarr/MTGDeckTester) are cheap to change technically, but any external link referencing the old path breaks. Treat the repo slug as settled.

Escape hatch

Lock-in: Low. Git history is portable by design — git remote can point anywhere. Issues, PR discussion, and Actions configuration are the only GitHub-specific artifacts, and none of those exist in a load-bearing way yet.

Migrating off GitHub would mean pushing the existing history to a new remote and, if adopted later, re-creating any GitHub Actions workflows in the new host's equivalent format. This is a same-day task at current project size.
